# 两固定病例四模型实际取点轨迹：本机接口分析

日期：2026-11-02。只分析既有实际 CUDA 轨迹；本轮无模型加载、forward、GPU 或训练。

## 结论

**最终 proxy 坐标稀疏、第一层直接邻域压缩与最终输出未充分利用接口支持同时存在；但实际计算图仍给绝大多数近接口输入点提供潜在传播路径，不能将结果归因为 FPS 将接口信息完全删除。**

更准确的研究问题是：接口支持能进入计算图，为何在局部聚合、全局表征、查询或解码后没有稳定转化为准确补全？本轮只取得几何及潜在依赖证据，没有记录激活、max-pool 赢家、梯度或因果干预，不能判定具体在哪层丢失有效特征。

## 潜在依赖如何计算

使用四次实际 KNN 的索引，不重新执行 NumPy FPS/KNN，不以近似索引替代实际轨迹：

1. graph1：N个原始点各向N查16邻居；每点特征可能依赖自身及其邻居。
2. graph2：512中心向N查邻居；包含其查询中心对应特征及邻居特征。
3. graph3：512向512聚合。
4. graph4：256向512聚合。

从全部最终256 proxy反向求支持索引并集，每层包括查询点自身和邻居分支；也将“某输入点是否靠近J”的布尔标记沿这些依赖路径前向传播。得到的是**可能的计算连接上界**，不是 max-pool 实际选中的通道、保留特征质量或因果重要性。

特征在 Conv、GroupNorm、激活、逐邻居 max-pool 中可能被压缩或混合；本轮未记录这些实际贡献。反向得到的原始支持点可以接近全部输入，也不代表每个proxy都精确保留每个支持点的几何。近接口点可到达proxy与模型有效利用它们是不同命题。

## 科研决策

- 不继续把“16k更多点”或“高曲率多采点”当作已证明有效路线；维持既有均匀8k基线。
- 不以256坐标约5%的覆盖率作为直接增加proxy、替换为Mamba或启动重训的充分依据。
- 本轮已将问题从“接口点完全无法到达模型”收窄到“接口局部几何的聚合、表征及输出利用可能不足”。这是一项有用的负面定位，尚不是机制因果结论。
- 下一阶段应先制定一个有限、可证伪的接口局部几何保留假设，再选择能区分聚合与输出问题的对照；不要扩展通用工程框架或反复更换采样器。若进一步记录特征贡献，需要另定范围，本轮不自动追加forward。
- A0221前景伪影与本次模型利用问题独立，不能通过模型改动证明其派生GT正确。
